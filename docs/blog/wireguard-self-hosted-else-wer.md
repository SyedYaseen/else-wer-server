# A Private Hostname Is Still a Public Problem

_Tags: wireguard, traefik, cloudflare, self-hosting_

> **Note:** This post was AI-generated by Claude, based on a real troubleshooting session I did with it. The commands, configs, errors and wrong turns are from that session. Some of the mistakes were mine and some were Claude's; both are kept in.

I wanted to open my audiobook server from my phone while away from home. I did not want it on the public internet. That sounds like one job. It turned into about eight: a VPN, two DNS records, a script that updates DNS, a certificate authority, a reverse proxy, a firewall, and a router setting I didn't know was missing.

Here is every step, including the ones that were wrong.

## The goal

[else-wer](https://github.com/SyedYaseen/else-wer-server) is a self-hosted audiobook server. It runs in Docker on an always-on Ubuntu box at home, which I'll call **the server** (LAN IP `192.168.1.18`). On the LAN it answers at `http://192.168.1.18:3030`.

What I wanted:

- `https://ew.syedyaseen.dev` opens else-wer from anywhere.
- Nobody on the internet can reach it, or even see that it exists.
- A valid HTTPS certificate, not a click-through warning.

The last point isn't about looks. else-wer's web app is a PWA, and its offline mode depends on a service worker. Browsers only allow service workers on a secure origin. Over plain `http://` there is no offline mode at all.

## The shape of it

```
phone / laptop
   │  WireGuard (UDP 51820), to wg.syedyaseen.dev = home public IP
   ▼
router ── port forward 51820/udp ──▶ server (wg0: 10.10.0.1)
                                         │
             ew.syedyaseen.dev = 192.168.1.18 (private IP, public DNS)
                                         ▼
                                  Traefik :443 (Let's Encrypt, DNS-01)
                                         ▼
                                  else-wer container :3000
```

Two hostnames do two different jobs:

| Hostname | Points to | Job |
|---|---|---|
| `wg.syedyaseen.dev` | home's **public** IP | where the VPN connects |
| `*.syedyaseen.dev` | server's **private** LAN IP | where the services live |

The rest of this post explains why each piece is there.

## WireGuard, briefly

WireGuard is a VPN built on one idea: **a packet that isn't signed by a key the server already knows gets no reply.** No handshake, no "connection refused", nothing. A port scanner sees silence.

That's why opening a WireGuard port is not like opening port 443. Forwarding 443 puts a web server in front of anyone who finds it. Forwarding 51820/udp puts in front of them something that ignores them.

The server side is small. `/etc/wireguard/wg0.conf`:

```ini
[Interface]
Address = 10.10.0.1/24
ListenPort = 51820
PrivateKey = <server private key>

[Peer]
# client: iphone
PublicKey = <iphone public key>
AllowedIPs = 10.10.0.2/32
```

And each client gets something like this:

```ini
[Interface]
PrivateKey = <client private key>
Address = 10.10.0.2/32
DNS = 10.10.0.1

[Peer]
PublicKey = <server public key>
Endpoint = wg.syedyaseen.dev:51820
AllowedIPs = 10.10.0.1/32,192.168.1.18/32
PersistentKeepalive = 25
```

The two `AllowedIPs` lines mean different things, and it took me a while to see it:

- On the **server**, `AllowedIPs` is _which source address this peer is allowed to send from_. The iPhone is `10.10.0.2`, and that's all.
- On the **client**, `AllowedIPs` is _which destinations go through the tunnel_. Here that's the server's tunnel address and its real LAN IP, and nothing else. Normal browsing stays on the phone's own connection.

Including `192.168.1.18/32` matters. `ew.syedyaseen.dev` resolves to the LAN IP, not the tunnel address. Without that route, the phone would send the request out over cellular to a private IP, and it would go nowhere.

Adding a client is a small script: generate a keypair, append a `[Peer]`, apply it live with `wg syncconf` (no restart), then write the client config and a QR code. The WireGuard app on a phone can scan the QR directly.

## Opening one port on the WAN

On the router: **forward UDP 51820 to `192.168.1.18`.** That's the only port forward in this whole setup.

On the server, `ufw` lets the tunnel in, and lets tunnel clients reach the services:

```sh
sudo ufw allow 51820/udp
sudo ufw allow from 10.10.0.0/24 to any port 443 proto tcp
sudo ufw allow from 10.10.0.0/24 to any port 3030 proto tcp
sudo ufw allow from 10.10.0.0/24 to any port 53
```

The tunnel subnet needs its own rules. A client's decrypted traffic arrives with source `10.10.0.x`, not a LAN address, even when it's headed for the server's LAN IP.

## Putting the public IP in Cloudflare

My ISP changes my public IP whenever it likes. `wg.syedyaseen.dev` has to keep up.

In Cloudflare, create an **A record** for `wg` pointing at the current public IP, with the proxy **off** (grey cloud, "DNS only"). Cloudflare's proxy only carries HTTP(S). WireGuard is UDP, so a proxied record would just break it.

Then a small script keeps it current. It asks ipify for the current public IP, reads the record from Cloudflare, and updates it only if they differ:

```bash
#!/usr/bin/env bash
set -euo pipefail
: "${CF_ZONE_ID:?}" "${CF_API_TOKEN:?}" "${WG_HOSTNAME:?}"

CURRENT_IP=$(curl -s --max-time 5 https://api.ipify.org)
AUTH="Authorization: Bearer ${CF_API_TOKEN}"
API="https://api.cloudflare.com/client/v4/zones/${CF_ZONE_ID}/dns_records"

RECORD=$(curl -sS "${API}?name=${WG_HOSTNAME}&type=A" -H "${AUTH}")
RECORD_ID=$(jq -r '.result[0].id' <<<"${RECORD}")
CF_IP=$(jq -r '.result[0].content' <<<"${RECORD}")

[[ "${CURRENT_IP}" == "${CF_IP}" ]] && { echo "No change (${CURRENT_IP})"; exit 0; }

curl -sS -X PUT "${API}/${RECORD_ID}" -H "${AUTH}" -H "Content-Type: application/json" \
  --data "$(jq -n --arg n "${WG_HOSTNAME}" --arg ip "${CURRENT_IP}" \
    '{type:"A",name:$n,content:$ip,ttl:60,proxied:false}')"
echo "Updated ${WG_HOSTNAME} -> ${CURRENT_IP}"
```

(The real one also checks `"success":true` on each response. Trimmed here.)

A systemd timer runs it every hour. The token comes from a root-only env file, not from the unit file:

```ini
# /etc/systemd/system/wg-wan-cloudflare-update.service
[Unit]
Description=Update wg.syedyaseen.dev with current public IP
[Service]
Type=oneshot
EnvironmentFile=/etc/wireguard/wg-cloudflare.env
ExecStart=/usr/local/bin/wg-wan-cloudflare-update

# /etc/systemd/system/wg-wan-cloudflare-update.timer
[Unit]
Description=Hourly WAN IP refresh for the WireGuard endpoint
[Timer]
OnBootSec=2min
OnUnitActiveSec=1h
[Install]
WantedBy=timers.target
```

```sh
sudo systemctl enable --now wg-wan-cloudflare-update.timer
```

## Why a wildcard record pointing at a private IP

The second record is the odd one. In Cloudflare:

```
*   A   192.168.1.18   DNS only
```

A private IP in public DNS looks like a mistake. It's intentional. The name resolves for anyone, anywhere, but it points at an address that only means something on my LAN or inside the tunnel. Someone outside gets `192.168.1.18`, tries it, and reaches whatever is at `192.168.1.18` on _their_ network, which isn't my server.

It's a **wildcard** because else-wer isn't the only thing on this box. `ew.`, and anything I add later, are all covered by one record. A new service gets a hostname by adding a router label, with no DNS change.

One catch: some mobile carrier DNS resolvers throw away public answers that point at private IPs. It's a protection against DNS rebinding attacks. So the phone asks the carrier's DNS, gets nothing, and the app acts as if the server is down. The fix is the `DNS = 10.10.0.1` line in the client config plus `dnsmasq` on the server, listening only on the tunnel:

```ini
# /etc/dnsmasq.d/wireguard.conf
interface=wg0
bind-dynamic
no-dhcp-interface=wg0
no-resolv
server=1.1.1.1
server=1.0.0.1
address=/ew.syedyaseen.dev/192.168.1.18
```

## Certificates for a server the internet can't reach

Let's Encrypt usually proves you own a domain by connecting to it (HTTP-01). Mine can't be reached from the internet by design, so that's out. The other option is **DNS-01**: the certificate client adds a TXT record through your DNS provider's API, Let's Encrypt checks the record, done. Nothing has to be reachable. That makes DNS-01 the only choice here.

It needs a **Cloudflare API token**. Create it under _My Profile → API Tokens_:

- Permission: **Zone → DNS → Edit**
- Zone resources: **only the zones it needs**

Don't use the Global API Key. A token scoped to DNS edits on one zone can do very little damage if it leaks.

## Traefik

Traefik was already running on this server for another domain, with its own Let's Encrypt resolver. I added a second one next to it. In `traefik.yaml`:

```yaml
entryPoints:
  websecure:
    address: ":443"

certificatesResolvers:
  cfdns:
    acme:
      email: you@example.com
      storage: /letsencrypt/acme.json
      dnsChallenge:
        provider: cloudflare
        propagation:
          delayBeforeChecks: 30s
          disableANSChecks: true
        resolvers:
          - "1.1.1.1:53"
          - "1.0.0.1:53"
```

The Traefik container gets the token as an environment variable:

```sh
# .env next to Traefik's compose file
CF_DNS_API_TOKEN=<token>
```

## Exposing else-wer

The service's compose file joins Traefik's network and describes its route in labels:

```yaml
services:
  else-wer:
    image: else-wer:latest
    container_name: else-wer
    restart: unless-stopped
    ports:
      - "3030:3000"          # keep direct LAN access as a fallback
    volumes:
      - else-wer-data:/data
      - /path/to/audiobooks:/audiobooks
    networks:
      - default
      - proxy-net
    labels:
      - "traefik.enable=true"
      - "traefik.docker.network=proxy-net"
      - "traefik.http.routers.elsewer.rule=Host(`ew.syedyaseen.dev`)"
      - "traefik.http.routers.elsewer.entrypoints=websecure"
      - "traefik.http.routers.elsewer.tls=true"
      - "traefik.http.routers.elsewer.tls.certresolver=cfdns"
      - "traefik.http.services.elsewer.loadbalancer.server.port=3000"

volumes:
  else-wer-data:

networks:
  proxy-net:
    external: true
```

A few of those lines are there because I got burned without them:

- `traefik.docker.network` tells Traefik which of the container's networks to use. With two networks, it can otherwise pick the wrong one.
- `default` has to be listed once you add any `networks:` key, or the container drops off its own project network.
- `loadbalancer.server.port` is the port _inside_ the container (`3000`), not the published host port.

That's the whole working setup. Getting there is the rest of the post.

## 1. The docs said "not started". The server disagreed.

I started by asking Claude to triage an earlier attempt that "didn't work". The repo docs said the WireGuard work was _planned, not started_. The server said otherwise: `wg0` was up, listening on 51820, and the Cloudflare update timer had been running for a week and was correctly tracking my IP.

I'd set it all up by hand on the server and never written it back into the repo. The repo's `deploy/wireguard/` folder was an older version for a Raspberry Pi I no longer have, using DuckDNS. So the docs weren't a little out of date. They described a different machine.

Lesson one: when docs and a live system disagree, check the live system. `systemctl list-timers`, `ss -ulnp` and `ip addr` settled it in seconds.

## 2. "Connected", with zero handshakes

The iPhone's WireGuard toggle said connected. Nothing loaded. Not else-wer at `192.168.1.18:3030`, not anything else.

My first theory, and Claude's, was the firewall. Another service's port had no `ufw` rule for the tunnel subnet, so we added one. Then I pointed out the obvious problem: else-wer's port **was** already allowed, and it failed too. A missing firewall rule couldn't explain both.

The real signal was in `wg show`:

```
peer: RWT95al7...
  allowed ips: 10.10.0.2/32
```

That's all it printed. A peer that has ever connected shows a `latest handshake:` line and a `transfer:` line. This one had neither. **Not one packet from the phone had ever reached the server.** Nothing past that point mattered: not ufw, not DNS, not routing.

The cause was a **missing port forward on the router.** The "connected" toggle on the phone only means the tunnel is configured. WireGuard has no connection state to report, and the server never replies to anything, so the phone can't tell that its packets are going nowhere.

If you do one thing from this post: **when a WireGuard tunnel "doesn't work", run `wg show` on the server first.** No handshake means the packets aren't arriving: check the port forward, and CGNAT, where your router's WAN IP doesn't match what `curl ifconfig.me` reports. Only once you see a handshake is the firewall worth looking at.

## 3. One Traefik, one Cloudflare token

My plan was for the new resolver to get its own token, scoped to just `syedyaseen.dev`, fully separate from the other domain's token.

That doesn't work. Traefik's Cloudflare DNS provider (via the lego library) reads its credentials from environment variables, **once per process**. Every `provider: cloudflare` resolver in one Traefik instance shares the same `CF_DNS_API_TOKEN`. Two resolvers can't use two different tokens.

The options were a second Traefik instance, or one token covering both zones. I edited the existing token in Cloudflare to add the second zone. It's still limited to DNS edits on exactly the two zones Traefik serves.

## 4. The config line that took down a different website

My first version of the resolver had this at the bottom, copied from an old planning doc:

```yaml
  cfdns:
    acme:
      # ...
      domains:
        - main: "syedyaseen.dev"
          sans: ["*.syedyaseen.dev"]
```

The idea was to fetch one wildcard certificate at startup. I restarted Traefik, and it went into a restart loop:

```
{"level":"error","error":"command traefik error: field not found, node: domains", ...}
```

`domains` isn't a valid field under `certificatesResolvers.<name>.acme`. It exists under `entryPoints.<name>.http.tls`, which was already set for the other domain, and each entrypoint gets only one default resolver.

The same Traefik serves my other site, so **that site was down** until the line came out. It was under a minute, but it was a production site going down over an audiobook hostname. The planning doc had never been tested against real Traefik, and neither of us checked it before restarting.

After removing the field, Traefik started cleanly and got certificates **per hostname** the first time each one was requested. That's `CN=ew.syedyaseen.dev`, not a wildcard. For one or two services that's fine. If you want a true wildcard certificate, the router-level `tls.domains[0].main` / `tls.domains[0].sans` labels are the place to ask for one. I haven't done that yet.

Before restarting a shared reverse proxy, check the new config against the docs for the Traefik version you actually run. Then watch the logs until it's up.

## 5. A router label that assumed too much

The else-wer compose overlay, written weeks earlier, had this comment:

```yaml
# No tls.certresolver on purpose: the router inherits the entrypoint's wildcard cert.
```

It would have inherited _something_. The `websecure` entrypoint's default resolver was the other domain's, pre-set to that domain's wildcard. A router with no resolver of its own would get Traefik's self-signed default certificate. The explicit line is required:

```yaml
- "traefik.http.routers.elsewer.tls.certresolver=cfdns"
```

## 6. `curl` returned 000, and nothing was wrong

Right after bringing the containers up:

```
ew.syedyaseen.dev: 000
subject=CN = TRAEFIK DEFAULT CERT
```

`000` means curl got no HTTP response at all. Here, curl rejected the certificate before it sent a request. Running with `-k` returned a `200` with the real page. Routing was fine; the certificate just didn't exist yet.

A minute later, `acme.json` had certificates for both hosts, and the real one was being served:

```
subject=CN = ew.syedyaseen.dev
issuer=C = US, O = Let's Encrypt, CN = YR2
```

DNS-01 is slow the first time. There's an ACME account to register and DNS changes to wait for. Give it a couple of minutes before you debug it. One trap: Traefik writes to a log file once `log.filePath` is set, so `docker logs traefik` shows nothing new. The ACME activity is in the file.

## 7. Adding a laptop: four errors in a row

The phone worked. Adding a laptop should have been one script run. It produced four errors.

**`scp: No such file or directory`.** The script runs under `sudo`, and `/etc/wireguard` is root-only (`700`). An `scp` as a normal user can't get into the directory at all, and SFTP reports that as "no such file", not "permission denied". Claude's first fix was to `chown` the client's folder, which doesn't help when the _parent_ folder is the one blocking. The real fix: the script puts a user-owned copy in your home directory and prints `scp` for that path.

**`A peer is missing a public key`.** To remove the broken client, Claude suggested:

```sh
sudo sed -i '/# client: loop /,/^AllowedIPs/d' /etc/wireguard/wg0.conf
```

That deletes from the comment down to `AllowedIPs`. The `[Peer]` header sits one line _above_ the comment, so it stayed, leaving an empty `[Peer]` with no key. WireGuard checks the whole file before applying, so the next script run failed. The script uses `set -e`, so it also stopped before writing the client config. The fix was deleting by line number after looking at `cat -n`. Don't use range regexes on a WireGuard config.

**`fopen: No such file or directory`.** Applying the fixed file by hand:

```sh
sudo wg syncconf wg0 <(sudo wg-quick strip wg0)   # fails
```

`<(...)` creates a file descriptor in _your_ shell. `sudo` closes extra file descriptors before starting the root process, so `wg` gets a path to a descriptor that no longer exists. Run the whole thing as root:

```sh
sudo bash -c 'wg syncconf wg0 <(wg-quick strip wg0)'
```

**`resolvconf: command not found`.** On the laptop, `wg-quick` saw `DNS = 10.10.0.1`, tried to hand it to `resolvconf`, didn't find it, and tore the tunnel down. On Arch, install `systemd-resolvconf` if `systemd-resolved` is running, otherwise `openresolv`. Or skip `wg-quick` and import the config into NetworkManager, which handles DNS itself:

```sh
nmcli connection import type wireguard file loop.conf
nmcli connection modify loop connection.autoconnect no
nmcli connection modify loop ipv4.dns-search "~syedyaseen.dev"
nmcli connection up loop
```

That last `dns-search` line sends only `*.syedyaseen.dev` lookups through the tunnel's DNS. That matters if you also run a commercial VPN, which brings me to…

## 8. Living next to another VPN

The laptop also runs Proton VPN. The two can run together, with some care:

- **Routes don't collide.** Proton takes the default route. My tunnel only claims `10.10.0.1/32` and the server's IP, and more specific routes win. With both up, WireGuard's traffic to my house travels inside Proton's tunnel. That works, with a bit more overhead.
- **A strict kill switch can block the handshake**, since it blocks traffic that isn't going through Proton.
- **"Whole LAN" mode is a trap on other people's WiFi.** Routing all of `192.168.1.0/24` through the tunnel breaks any café or hotel network that also uses `192.168.1.x`, which is a lot of them. You lose the local router and your internet. Limiting a laptop to the server's address is safer.
- **Hotspot traffic doesn't use the phone's tunnel.** On iOS, the VPN only covers the phone's own traffic. A laptop on its hotspot needs its own tunnel. And the server would reject it anyway, because each peer is locked to its own `/32`.

Also: testing from home WiFi can fail when everything is right. The client connects to your own public IP from inside your own network, and plenty of consumer routers won't loop that back in (it's called hairpin NAT). Test from a phone hotspot.

## Testing it

From a device off the home network, with the tunnel up:

```sh
# on the server: did anything arrive?
sudo wg show wg0                 # look for "latest handshake"

# on the client
ping -c 3 10.10.0.1
dig +short ew.syedyaseen.dev     # 192.168.1.18
curl -I https://ew.syedyaseen.dev

# certificate is the real one, not Traefik's default
echo | openssl s_client -connect ew.syedyaseen.dev:443 -servername ew.syedyaseen.dev 2>/dev/null \
  | openssl x509 -noout -subject -issuer
```

And from a device that is **not** on the tunnel or the LAN, `https://ew.syedyaseen.dev` should time out. That's the point of the whole thing.

## What I would tell myself at the start

1. **`wg show` before anything else.** No handshake means a network problem upstream: port forward, CGNAT, hairpin NAT. Firewall rules come later.
2. **A tunnel toggle saying "connected" means nothing.** WireGuard is silent by design, and that includes being silent about failures.
3. **Two hostnames, two jobs.** One tracks the public IP for the VPN. A wildcard points at the private IP for services.
4. **DNS-01 is the only certificate option** for a service the internet can't reach, and one Traefik process gets one Cloudflare token.
5. **Planning docs aren't config.** A snippet nobody has run can take down whatever else shares that proxy.
6. **Set `tls.certresolver` on the router explicitly.** Don't count on inheriting it.
7. **`sudo` and `<(...)` don't mix.** Use `sudo bash -c '...'`.
8. **Write the live setup back into the repo right away.** Half of this session was rediscovering work I had already done.
